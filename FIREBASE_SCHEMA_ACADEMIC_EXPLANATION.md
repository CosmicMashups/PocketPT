# Firebase Database Schema: Class Diagram Explanation

## Overview

The PocketPT application employs a cloud-based database architecture utilizing Google Firebase Firestore, a NoSQL document-oriented database system. The schema is organized into seven primary collections, each representing a distinct domain entity within the rehabilitation and physical therapy management system. Each collection follows a flat hierarchical structure where documents are identified by user identifiers, ensuring data isolation and efficient querying patterns. The architectural design prioritizes scalability, data integrity, and cross-device synchronization capabilities while maintaining a clear separation of concerns across different functional domains.

## Collection 1: Users Collection

The `users` collection serves as the foundational entity in the database schema, representing the core user account information within the system. This collection implements a document-per-user pattern, where each document is uniquely identified by the user's authentication identifier (`userId`), which corresponds to the Firebase Authentication User ID. The class structure encompasses essential user profile attributes including `firstName` and `lastName` as string-based identifiers, an `email` attribute serving as the primary communication channel and authentication credential, and an optional `profilePicture` attribute for visual user representation. Additionally, the collection maintains temporal metadata through `createdAt` and `lastUpdated` timestamp fields, enabling audit trails and temporal data management. The `hasCompletedAssessment` boolean attribute functions as a state indicator, tracking whether the user has completed the initial rehabilitation assessment process. This collection establishes the primary key relationship for all subsequent collections, as each user document serves as the root entity from which all user-specific data collections are referenced through the shared `userId` identifier.

## Collection 2: Rehabilitation Collection

The `rehabilitation` collection represents the core therapeutic intervention structure, encapsulating personalized rehabilitation plans assigned to individual users. This collection follows a document-per-user architecture, where each document is keyed by the user identifier and contains a dynamic set of rehabilitation plans. The class structure employs a flexible schema design where plans are stored as incrementally numbered properties (`Plan1`, `Plan2`, `Plan3`, etc.), allowing for multiple concurrent or sequential rehabilitation programs per user. Each plan is structured as an array containing two distinct map objects: the first map stores exercise references using incrementally numbered keys (`exercise1`, `exercise2`, `exercise3`, etc.) with corresponding exercise identifier values, while the second map stores treatment references using similar incremental key patterns (`treatment1`, `treatment2`, `treatment3`, etc.) with treatment identifier values. This design pattern implements a normalized data storage approach, storing only reference identifiers rather than complete exercise or treatment data, thereby reducing data redundancy and storage overhead. The collection maintains a `lastUpdated` timestamp field to track the most recent modification to the rehabilitation plans, and includes a `userId` attribute to maintain referential integrity. The exercise and treatment counters operate independently within each plan, allowing for flexible plan composition where the number of exercises and treatments may vary without structural constraints.

## Collection 3: Progress Collection

The `progress` collection encapsulates quantitative metrics and statistical data pertaining to user engagement and rehabilitation outcomes. This collection implements a document-per-user pattern, maintaining comprehensive progress tracking attributes that enable longitudinal analysis of user performance. The class structure includes a `title` attribute representing a user-defined progress label, accompanied by a `titleColor` attribute for visual customization purposes. Quantitative metrics are captured through integer attributes including `streak`, representing consecutive days of exercise completion, `totalDays` tracking the cumulative number of active days, `totalExercises` maintaining a count of completed exercise sessions, and `totalSeconds` recording the aggregate duration of exercise activities in seconds. The collection incorporates a `notes` attribute as a text field for qualitative observations and user annotations, while the `lastExerciseDate` timestamp attribute tracks the temporal context of the most recent exercise activity. Temporal metadata is maintained through `lastUpdated` and `userId` attributes, ensuring data provenance and referential integrity. This collection serves as the primary source for generating progress visualizations, statistical reports, and motivational feedback mechanisms within the application.

## Collection 4: Assessment Collection

The `assessment` collection stores the initial clinical evaluation data collected during the user onboarding process, forming the foundation for personalized rehabilitation plan generation. The collection follows a document-per-user architecture, where each document contains comprehensive assessment attributes that inform therapeutic intervention strategies. The class structure includes goal-oriented attributes such as `rehabGoal`, representing the primary rehabilitation objective, and muscle-specific attributes including `generalMuscle` and `specificMuscle` for anatomical localization of the condition. Pain assessment is captured through multiple dimensions: the `painScale` attribute stores a numerical value on a standardized 0-10 scale, while `painLevel` provides categorical classification, `painType` describes the qualitative nature of the pain, and `painDuration` indicates the temporal characteristics of the condition. Boolean attributes `isInjured` and `isAssessed` serve as state indicators, tracking injury status and assessment completion respectively. The collection maintains `lastUpdated` and `userId` attributes for temporal tracking and referential integrity. This collection functions as the primary input for algorithmic rehabilitation plan generation, enabling the system to match appropriate exercises and treatments based on clinical assessment criteria.

## Collection 5: Settings Collection

The `settings` collection manages user preferences and notification configuration parameters, implementing a document-per-user pattern to maintain personalized application behavior. The class structure focuses on notification and reminder functionality, with boolean attributes controlling various alert mechanisms: `isDailyReminder` enables or disables daily motivational notifications, `isStreakAlert` controls notifications related to exercise streak maintenance, and `isExerciseReminder` activates scheduled exercise reminder functionality. When exercise reminders are enabled, temporal scheduling is managed through `exerciseReminderHour` and `exerciseReminderMinute` attributes, which store integer values representing the 24-hour format time specification (0-23 for hours, 0-59 for minutes). The collection includes standard metadata attributes `lastUpdated` and `userId` for temporal tracking and referential integrity. This collection enables the application to provide personalized user experiences through configurable notification systems, supporting user engagement and adherence to rehabilitation protocols.

## Collection 6: Pain History Collection

The `painHistory` collection maintains a chronological record of pain assessment entries, enabling longitudinal tracking of pain levels and patterns over time. The collection implements a document-per-user architecture, where each document contains an `entries` array attribute that stores a collection of pain record objects. Each entry within the array is structured as a composite object containing three primary attributes: a `date` timestamp attribute providing temporal context, a `painScale` integer attribute recording the numerical pain assessment on a 0-10 scale, and a `painLevel` string attribute storing categorical pain classification. The collection includes a `lastPromptedDate` timestamp attribute that tracks when the user was last prompted to record pain data, facilitating intelligent prompting algorithms that prevent notification fatigue. Standard metadata attributes `lastUpdated` and `userId` are maintained for temporal tracking and referential integrity. This collection supports clinical analysis by providing historical pain data that can be used to evaluate treatment effectiveness, identify pain patterns, and inform therapeutic adjustments. The array-based structure allows for efficient chronological queries and enables the generation of pain trend visualizations.

## Collection 7: Exercise History Collection

The `exerciseHistory` collection maintains comprehensive records of exercise completion activities, providing detailed tracking of user engagement with prescribed rehabilitation exercises. The collection follows a document-per-user pattern, where each document contains an `entries` array attribute storing a collection of exercise record objects. Each entry within the array represents a single exercise completion event and includes multiple attributes: a `date` timestamp attribute for temporal context, `exerciseId` and `exerciseName` string attributes for exercise identification and display purposes, `sets` and `reps` integer attributes recording the quantitative parameters of the exercise session, a `durationSeconds` integer attribute capturing the temporal duration of the exercise, and a `status` string attribute indicating the completion state (e.g., 'completed', 'skipped', 'partial'). The collection maintains `lastUpdated` and `userId` attributes for temporal tracking and referential integrity. This collection serves multiple analytical purposes, including adherence monitoring, performance tracking, progress evaluation, and the generation of exercise completion statistics. The array-based structure enables efficient querying for specific time periods, exercise types, or completion patterns, supporting both user-facing progress displays and backend analytical processes.

## Schema Relationships and Design Patterns

The database schema implements several key design patterns that enhance scalability, maintainability, and query performance. The flat collection structure, where each collection maintains documents keyed by user identifier, eliminates the need for complex nested queries and enables efficient horizontal scaling. The normalized approach employed in the rehabilitation collection, where only reference identifiers are stored rather than complete exercise or treatment data, reduces data redundancy and storage costs while maintaining referential integrity through external data sources (CSV files). The array-based structures in the pain history and exercise history collections enable efficient chronological queries and support time-series analysis without requiring subcollection complexity. The consistent inclusion of `userId` and `lastUpdated` attributes across all collections facilitates data synchronization, audit trails, and referential integrity maintenance. This architectural design supports the dual-database strategy employed by the application, where Firebase serves as the cloud persistence layer while local Hive storage provides offline functionality, with the schema structure enabling seamless bidirectional synchronization between these storage systems.
